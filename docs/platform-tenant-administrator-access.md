# Platform tenant-administrator access

The platform-admin role currently exposes tenant provisioning and platform configuration, while organisation user/role pages require tenant grants. Provide a dedicated platform administration surface for tenant administrators and their fixed system role.

1. Add explicit platform tenant-access read/manage permissions and a bounded Identity API: select a tenant, read its administrator roster/details, invite an additional administrator, update their display name, resend a pending invitation, suspend/restore access and revoke the tenant-admin assignment. Protect the last active administrator. Use the existing user, invitation and assignment models, audited transactions, fresh platform-operator authorization, target-tenant isolation, optimistic checks and idempotent commands. Add role/permission metadata for the immutable tenant-admin system role.
2. Keep the permission catalogue, system role seed, documentation, shared-library version/consumer locks and generated Identity SDK synchronized. Build permission-aware platform menus/cards and administrator directory/detail/editor pages with the existing layout, controls and styles. Support tenant selection, View/Edit kebabs, role/permission links, validation, recoverable commands and filtered return navigation.
3. Run focused native API, scope, replay, last-administrator and role-seed tests; run UI/type checks and browser reviews. Review security and simplify, fix findings, build Console, apply the updated platform-admin seed locally and verify service readiness.

Only tenant-admin assignments are manageable through this boundary. Ordinary tenant users, arbitrary roles, company data and financial records remain on their existing scoped APIs. Permissions are a read-only code catalogue and the tenant-admin system role is immutable. Invitation verification continues through Authentik.

No ORM model or DDL change is planned. Existing unrelated edits, local paths and publishing state are preserved.

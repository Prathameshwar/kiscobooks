# Advanced product creation: 10-scenario test plan

Status: proposed plan only. No scenarios executed, fixtures created, configuration published or VM changed for this request.

Target: Product Profile + SKU creation with `product_family_sku_enabled = true`. Exercise all four entry steps and creation progress. Expectations are test oracles, not findings from execution.

## Preparation for the later test run

- Use an isolated test company and a second company for permission/ownership checks. Keep Advanced mode enabled for every baseline scenario. Capture the effective company configuration, capability flags, Product Type revision, field permissions and policy/source versions before each run.
- Prepare separate configuration snapshots for the scenarios. Apply each snapshot through the normal configuration lifecycle and wait for its effective options to appear before starting. Do not change production configuration to simulate a case.
- Use published, compatible Product Types, attributes/options, units, groups, brands, categories, manufacturers/sites, price levels, tax classifications/rates and tracking profiles. Record their actual IDs in the execution sheet; the names below are fixture labels.
- Let `T` be the execution date and `D` the test company's books-begin date. Opening tests use exactly `D`. Ensure the warehouse, financial year, native stock posting and applicable source/policy evidence are ready for `D`; current authoring/pricing sources must also be valid for `T`.
- Currency INR; ordinary quantity precision 0/increment 1; price display precision 2; price basis 1 base unit unless a scenario says otherwise. Enter monetary values as exact decimal strings. All entered purchase references use source `QA supplier quotation`; all entered MRP uses jurisdiction `IN` and source `QA manufacturer price list`.
- Use a unique run prefix on Profile codes, SKU codes, batch codes and identifiers. Reset to a fresh draft before each negative variant. Change one invalid input at a time so the cause is unambiguous.
- Every scenario supplies a required Profile code, for example `QA01-BASIC` through `QA10-PRICES`, and a valid compatible group such as `QA Products` or `QA Services`. Prefix those codes for each run. Unless stated otherwise, enable both Sale and Purchase on each SKU and choose the scenario's published Type revision explicitly.
- Run valid cases with an authorized creator. Run denial variants with a separate test role. Capability enablement and field permission are separate prerequisites.

## Checks applied across the scenarios

1. **Four entry steps:** correct visible/required/disabled fields, meaningful labels, reference names, typed values, per-SKU selection and complete review summaries. Back/Continue preserve entered data. Save draft remains possible for incomplete work where allowed.
2. **Numeric negatives:** in scenarios 02, 05 and 07 separately try `-1`, `abc`, `12.34567` and an amount above the storage range. Also enter a valid amount, replace it with invalid text and attempt Save/Continue/Create: the prior valid amount must not be submitted silently. Positive opening cost, purchase reference and MRP cannot be zero; zero selling prices follow the applicable native price policy.
3. **Configuration consumption:** capture actual options/defaults and their versions; verify disabled, optional, required and inherited resolved behavior. Changing a dropdown preserves focus/data, shows contextual loading and avoids a full-page reload. Log request counts so redundant reloads can be distinguished from necessary dependent metadata requests.
4. **Progress:** visible from the initial request; messages identify the task/SKU; setup, price, activation and stock confirmations remain separate. No simulated percentage, false completion or premature stock-posted claim. Skipped openings use clear wording. Partial/missing receipts do not count as completed work.
5. **Failure and recovery:** readable message and correct field/step; values and completed native work retained; controls prevent concurrent duplicate submissions. Correct only the remaining editable setup. Completion clears stale failures and focuses the result.
6. **Saved facts:** inspect Profile/SKUs, attributes, unit bindings, tax setup, purchase references, published sale prices, MRP, batch/serial details and opening state. Compare exact amounts/quantities with independent Decimal calculations. Confirm native stock quantity/value and linked posted opening evidence; a success banner alone is insufficient.
7. **Presentation:** every scenario at desktop 1440px/light theme; representative long-form/variant/batch/failure cases at 768px and 390px in light, dark and ledger themes. Check spacing, overflow, sticky actions, keyboard focus, announcements and reduced-motion behavior. Browser availability must be resolved before visual execution is claimed.

Interpret negative results by phase. Locally detected invalid fields should block the definition request. A native-only setup or opening rejection can leave an already saved Profile/SKU; opening checks occur after activation, so valid SKUs may already be active while their opening remains incomplete. Do not expect an automatic rollback of saved product identity. Verify retained progress, accurate completion messages, absence of unintended stock effects and recovery of the same creation.

## Proposed execution order and evidence

Run 01-04 first, then 05-07, then 08-09. Finish with the scope probe in 10. For each scenario, establish the valid baseline before changing one negative condition, except inherently denied-role cases.

Begin with controlled UI/API fixtures to isolate configuration and progress behavior. Follow with an integrated run against isolated native services to verify persisted facts and stock effects. Mocked success is not evidence of an actual stock posting. A VM-based test run remains a later decision; this plan does not authorize a VM update.

Record: scenario/subcase, configuration/capabilities/permissions, resolved versions, exact entered data, screenshots and request sequence, creation/Profile/SKU IDs, resulting native facts, expected versus actual outcome, severity and reproduction steps. Classify failures as configuration preparation, missing authoring coverage, UI/validation, native contract or recovery/posting issues before proposing a fix.

Exit criteria: valid scenarios have the expected native state; negative inputs produce understandable rejection without unintended stock effects or duplicate creation; recovery resumes one creation; visual checks have evidence. Report blocked and unsupported cases explicitly. No scenario is marked passed merely because a progress panel reports success.

Scope limit: these 10 scenarios provide targeted coverage, not every combination. The 64-SKU limit, 64-batch limit, 200-serial limit, performance, compound/measured conversion entry and downstream voucher pricing remain separate follow-up coverage unless a finding makes them necessary.
